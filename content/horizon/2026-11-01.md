### [Parameter Labs 披露 ChatGPT 账户接管漏洞链](https://simonwillison.net/2026/Oct/31/how-we-took-over-chatgpt-accounts/) ⭐️ 8.0/10

Parameter Labs 披露了一条针对 ChatGPT HTML 预览（原 Canvas）沙箱 iframe 的逃逸攻击链：沙箱内不可信代码可通过 postMessage\(\) 触发父页面中 MathLive 虚拟键盘的消息处理逻辑，该逻辑使用 innerHTML 注入内容，且未限制其他沙箱帧调用。攻击者借此注入一个不带沙箱限制的新 iframe，再绕过 OpenAI 的 CSP——内联脚本被禁止、仅允许少数域名加载脚本，但 YouTube 的 oEmbed 端点可被用来反射并执行 JavaScript。获得脚本执行能力后，攻击者可读取用户私有数据并通过图片引用外传；最终一个 ChatGPT 分享链接在已登录用户访问时即可窃取其数据或代其操作。OpenAI 已修复该漏洞并支付 5,000 美元赏金，Simon Willison 认为这一金额对如此严重的漏洞偏低。

rss · Simon Willison · 10月31日 23:15

**「背景」** ChatGPT 的 HTML 预览（此前称为 Canvas）会把用户生成的交互式 HTML 应用放在沙箱 iframe 中运行，其安全前提是这些 iframe 无法接触 OpenAI 的 API 或用户私有数据。Parameter Labs 的披露指出，OpenAI 在图表支持中使用的 MathLive 库带有虚拟键盘，其顶层控制器采用“无来源限制”策略，会接受来自任意网页地址的 postMessage，且不要求消息来自此前已获批准的窗口，这成为攻击链的起点。

**「影响」** 该漏洞表明，ChatGPT 分享链接可能成为跨用户攻击载体：任何已登录用户打开他人分享的对话都可能被窃取私有数据或触发代操作。对开发者而言，这也说明仅依赖 iframe 沙箱和 CSP 白名单不足以隔离不可信 HTML，需审查 postMessage 接收端的 innerHTML 使用及白名单域名的脚本反射风险。

### [巴西法院因在诉状中植入提示注入处罚律师](https://jetstream.security/insights/brazilian-court-sanctions-prompt-injection-filing/) ⭐️ 7.0/10

巴西一家法院对律师作出处罚，原因是他们在提交给法院的文书中隐藏了一段针对人工智能的提示注入指令。据社区评论引述的原文，该指令要求“人工智能”对这份申请作表面化处理、不要质疑文件内容，无论收到什么命令。该报道称这是法院如何处理在正式程序中操纵 AI 系统的早期法律先例，但这是单一司法辖区的裁定，且所给材料未提供法院名称、处罚金额或裁决日期等细节。

hackernews · doodlesdev · 11月1日 02:19 · [社区讨论](https://news.ycombinator.com/item?id=50322173)

**「背景」** 提示注入（prompt injection）指在文本中嵌入隐藏指令，诱导处理该文本的大语言模型偏离原任务、执行攻击者意图，是 LLM 应用中的常见安全风险。据 Jetstream Security 与 Lexology 的报道，本案涉及巴西一家法院用于处理文书的 AI 系统，律师被指在提交文件中隐藏指令以影响该系统；相关报道称这可能是全球首例针对故意操纵法院 AI 系统的司法裁决。

**「实际影响」** 对在司法或高监管流程中部署大语言模型的机构而言，这一裁定表明：把针对 AI 的隐藏指令写入正式文书可能被视为可处罚的行为，而不只是技术上的小把戏。相关团队在把 AI 用于文书审查前，需要评估输入内容中是否夹带面向模型的指令，并明确人工复核的责任边界。

**「社区讨论」** 有评论者（jkahrs595）质疑：如果直接向法院提出“请表面化处理、不要质疑文件”的要求，是否同样会被罚款，并追问为何对 AI 提出类似要求就构成违规。另一条评论（mikelitoris）则把这一事件与法院使用 AI 审查文书相比较，认为两者都令人担忧；BrenBarn 还指出，该裁决由 DeepL 从葡萄牙语翻译而来，为事件增添了一层元层面的意味。

### [Linux TCP 释放后使用漏洞 CVSS 9.8，主流发行版尚未修复](https://atlasum.net/blog/cve-2026-98432-linux-ipv4-tcp-uaf) ⭐️ 7.0/10

Linux IPv4/TCP 协议栈存在一个释放后使用（use-after-free）漏洞，编号 CVE-2026-98432，CVSS 评分 9.8。据社区讨论，该漏洞并非仅限 MPTCP，而是通用的释放后使用问题；利用需要多核并行处理数据包，单核系统或将包处理绑定到单核的系统不受影响。截至讨论时，Ubuntu 与 RHEL 均未发布补丁，社区引用的两家厂商安全页面显示修复尚未就绪。

hackernews · oger · 10月31日 19:16 · [社区讨论](https://news.ycombinator.com/item?id=50319143)

**「背景」** 该漏洞位于 Linux 内核 IPv4 网络子系统的 TCP 连接请求处理路径，属于释放后使用（use-after-free）问题。据 AWS 安全公告，受影响的是内核 4.4 及以后版本；红帽的安全公告称，远程未认证攻击者可利用 TCP 连接请求处理中的竞态条件触发远程代码执行。

**「影响与缓解」** 社区指出，通过互联网直接利用的可能性较低，因为多数 ISP 路由器会丢弃带 IP options 字段的数据包；Red Hat 认为自行丢弃带 IP options 的数据包有帮助，但并非完整缓解措施。使用 AWS 负载均衡、CloudFront、API Gateway 等服务的用户，在遵循最佳实践时不直接接收来自不可信来源的 TCP 连接，AWS 表示正在更新这些服务的底层基础设施。运行受影响内核的服务器管理员需关注发行版补丁进展，并评估上述临时缓解手段。

**「社区讨论」** 有评论者批评 HN 编辑标题时删去“Linux”，认为这掩盖了漏洞仅影响 Linux、不影响 BSD、macOS 和 Windows 的关键信息。另有评论质疑 Ubuntu 和 RHEL 作为主打服务器场景的发行版为何迟迟未修复，并附上两家厂商的 CVE 页面作为佐证。

### [技术公司中建立声誉的快慢两条路](https://seangoedecke.com/how-to-get-assigned-interesting-work/) ⭐️ 7.0/10

rss · Sean Goedecke · 11月1日 00:00

**「背景」** 在技术公司里，想获得好声誉就得参与重要项目，但重要项目往往只交给已经有好声誉的人，这让不少工程师陷入“永远坐冷板凳”的困境。作者认为，问题的根源不在正式流程，而在于管理者的真实激励：他们更在意自己能否交付成果、维护个人声誉，因此倾向于把高风险的高曝光项目交给已知可靠的人，而不是按轮岗或公平原则分配。

**「方案」** 作者把出路分为慢和快两类。慢路径是经典的“棘轮效应”：先稳定交付小而低风险的工作，主动让经理和团队知道，再逐步争取风险稍高的任务，同时避免任何会强化“不可靠”印象的失误，最终被视作可以托付重要工作的安全人选。这条路不试图说服经理改变激励，而是让自己看起来与经理的利益一致，但耗时数月甚至数年，期间可能遭遇坏运气、经理离职或技术环境变化。快路径则伴随风险：一是与 skip-level（经理的上级）建立关系，让对方主动推荐你，但高层管理者擅长识别刻意讨好，弄巧成拙反而有害；二是自己发现并实施“侧注”项目，制造出无需被分配的工作，代价是可能白费时间，且许多经理会因团队工作不在自己掌控中而不悦；三是赢得工程师同事的认可，在健康团队中，同事很快能判断谁技术过硬并告知经理，从而加速获得重要工作，但在糟糕团队中同事可能识别不出强人，在有毒团队中甚至会诋毁能干的同事。作者强调，这些快路径都是危险建议，需自行承担后果。

**「启示」** 作者的核心结论是：如果有趣的工作总流向别人，你面对的是声誉问题，而非个人恩怨；与其在 1:1 中向经理抱怨不公平，不如设法让分配工作看起来符合经理自身的利益——无论是借助 skip-level、自创项目，还是先赢得经理信任的工程师的认可。技术公司本就不以公平为目标，而是以赚钱为目标。
