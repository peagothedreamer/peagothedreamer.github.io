> 仓库：[peagothedreamer/obsidian-rag](https://github.com/peagothedreamer/obsidian-rag)

学期初把《电子电路基础》的课件整理进了 Obsidian，一章一个文件夹、一节一个文件，前后攒了 346 篇 Markdown。整理的时候很爽，查的时候很痛苦：想在复习时找「体效应为什么让阈值电压变高」，只记得大概意思，不知道它在哪一节。用 Obsidian 自带的全文搜索，得先猜中关键词；换个说法就搜不到。

于是有了 obsidian-rag：一个跑在本地、答案带引用、可以量化评测的 RAG 问答 demo。核心检索管线全部手写，没有 LangChain，没有向量数据库。

## 整体结构

```text
离线：构建索引
  346 篇 Markdown
      ├─ 清洗：去 frontmatter、图片嵌入，[[双链]] 还原为纯文本
      ├─ 标题感知切块 → 1188 个 chunk（≤800 字，重叠 100 字）
      ├─ bge-m3 编码   → embeddings.npy（1188 × 1024 float32，约 4.9MB）
      └─ 记录文件 sha256 → state.json

在线：问答
  问题 ─┬─ bge-m3 编码 ──→ 向量召回 top-20 ─┐
        └─ jieba 分词  ──→ BM25 召回 top-20 ─┴→ RRF 融合 → 精排取 top-5
                                                          ├→ DeepSeek 生成带 [n] 引用的答案
                                                          └→ Streamlit 展示来源
```

## 决定一：切块利用笔记本身的标题结构

笔记本来就是「章 → 节 → 小标题」的树形结构，没必要退化成定长切块。切块器按 ATX 标题切段（代码块里的 `#` 不参与识别），每个 chunk 的正文前缀是「笔记名 > H1 > H2」，embedding 时保留上下文；超长章节按段落打包，相邻块重叠 100 字，小于 50 字的碎块并回上一块。

一个细节：`chunk_id` 由「笔记路径 + 标题路径 + 序号」哈希得到，不依赖内容。这样笔记正文改了，chunk 的 ID 不变，评测集里的金标引用也不会全部失效。

## 决定二：混合检索，RRF 只排序不截断

纯向量对同义改写友好，纯 BM25 对术语和公式名友好，两路各取 top-20，用 RRF（k=60）融合。融合之后交给 bge-reranker-base 精排，取 top-5 送进生成。

这里踩过最大的坑，见下文「一次真实的召回 bug」。

## 决定三：这个规模不用向量数据库

1188 个 1024 维向量一共约 4.9MB，一次全量点积是亚毫秒级。这个量级下：

- numpy 暴力检索是精确的，ANN 反而引入召回损失；
- 不需要维护 `FAISS index ↔ chunk_id` 的映射，少一层状态；
- 少一个依赖，Windows 上少一类安装问题。

真正的瓶颈在 CPU 精排，约 7–11 秒一题。规模到十万级再考虑 FAISS / hnswlib，现在上 ANN 属于给问题配答案。

## 决定四：增量索引

`state.json` 记录每篇笔记的 SHA256：内容没变的笔记直接复用旧 chunk 和旧向量，改一篇只重嵌那一篇；删掉的笔记自然退出索引；解析失败的不写入状态，下次自动重试。全量建索引 CPU 上 3–5 分钟，日常改一篇笔记只需几秒。

## 评测：自己出题，专挑不好搜的

只看几个 demo 问答说明不了问题，所以自建了两套题：

- **基础集 46 题**：按笔记标题出题，关键词重合度高，用作回归基线；
- **改写集 78 题**：刻意不用标题里的原词。比如不问「什么是体效应」，而问「MOS 管的源极没有和芯片衬底接到同一个电位时，开启它所需的栅压为什么会变高？漏极电流会怎样？」——金标仍然是体效应那一节。

指标是 Recall@5（top-5 按笔记去重后命中金标的题目占比）和 MRR@10。

### 基础集（46 题）

| 配置 | Recall@5 | MRR@10 |
|---|---|---|
| vector | 0.978 | 0.905 |
| bm25 | 0.957 | 0.846 |
| hybrid | 0.978 | 0.918 |
| hybrid + rerank | 1.000 | 0.889 |

### 改写集（78 题）

| 配置 | Recall@5 | MRR@10 |
|---|---|---|
| vector | 0.705 | 0.569 |
| bm25 | 0.667 | 0.518 |
| hybrid | 0.679 | 0.580 |
| hybrid + rerank | **0.872** | **0.683** |

两套题的差距本身就是一个发现：基础集上四种配置几乎打平，说明标题关键词重合时怎么搜都对；改写集才拉开差距，精排把 Recall@5 从 70.5% 抬到 87.2%。

## 一次真实的召回 bug：RRF 把正确结果截掉了

早期实现里，两路召回各取 top-20，RRF 融合后直接取前 20 送精排。看起来很自然，但 RRF 会把「只被一路召回」的结果压下去。

一个具体案例：某题的金标笔记在 BM25 里排第 17，在向量里不在前 20；RRF 融合后掉到第 30，于是根本进不了精排。而它其实被召回了——所谓召回失败，实际是候选池截断。

修复方法一句话：**RRF 只用于排序，候选池取两路并集（≤40）再精排。** 修完之后，这道题的金标直接排到第 1。

这件事之后我对「召回率」和「送进下一级之前还剩多少」区分得更清楚了：中间任何一级的截断，都会伪装成上一级的召回问题。

## HyDE：有效，但没进主链路

改写集上纯向量只有 70.5%，说明问题与笔记之间存在表达鸿沟。HyDE 的思路是让 LLM 先写一段假设答案，再用假设答案的向量去检索——内容可能是虚构的，但表达方式更接近真实笔记。

对比四种输入（只测纯稠密检索，隔离变量）：

| 模式 | Recall@5 | MRR@10 |
|---|---|---|
| 原问题 | 0.705 | 0.569 |
| 单段假设答案 | **0.846** | 0.646 |
| 问题 + 假设答案 | 0.795 | 0.649 |
| 多段假设答案向量平均 | 0.808 | **0.661** |

提升很明显：Recall@5 从 70.5% 到 84.6%。但把 HyDE 接进「混合检索 + 精排」之后：

| 配置 | Recall@5 | MRR@10 |
|---|---|---|
| hybrid + rerank | 0.872 | 0.683 |
| HyDE + hybrid + rerank | 0.872 | 0.692 |
| HyDE + hybrid（不精排） | 0.769 | 0.636 |

78 题里 1 胜 1 负 76 平，ΔMRR +0.009，95% 置信区间跨 0。结论是：HyDE 确实改善了第一阶段候选（不精排时把混合检索从 0.679/0.580 提到 0.769/0.636），但精排已经把这个缺口补上了，额外的生成成本和更大的精排候选池并不划算。

所以 HyDE 作为实验代码保留（`hyde/`），没有进入默认问答链路。下一步值得验证的是：限制精排预算（比如只精排 top-20）时，HyDE 的价值会不会重新出现。

## 生成与界面

- 生成用 DeepSeek，prompt 强制答案标注 `[n]`，答案下方列出「笔记路径 + 标题路径」，可以点回 Obsidian 原文。
- 模型偶尔输出 `\( \)` / `\[ \]` 定界符，渲染前统一转成 Streamlit 支持的 `$...$` / `$$...$$`。
- 不配 API key 也能跑：自动退化为「仅检索模式」，评测不受影响。
- Streamlit 单页界面，首次提问要加载模型约 10–20 秒。

## 已知局限

- 只有一门课，领域窄，不能说明通用检索能力；
- 78 条改写题仍是作者自己出的，有选题偏差；1 题约等于 1.3 个百分点，小样本只看趋势；
- 图片、PDF 附件没解析，公式只作为文本参与检索；
- CPU 精排 7–11 秒一题，交互体验一般。

## 下一步

- 改写集扩到 100+，加入跨章节题和计算题；
- 在 top-20 精排预算下重测 HyDE；
- 对比 bge-large-zh-v1.5、gte-multilingual-base 等 embedding；
- ONNX / 量化精排，把延迟压下来；
- 点击引用直接跳转 Obsidian 对应笔记。

## 复现

```bash
git clone https://github.com/peagothedreamer/obsidian-rag.git
cd obsidian-rag
uv sync
# 把同结构的课程笔记放进 notes/电子电路基础/
uv run python -m rag.index          # 建索引，首次约 3–5 分钟
uv run python -m rag.eval --questions eval/questions.paraphrase.jsonl --out reports/eval/paraphrase.md
uv run streamlit run app.py --server.address 127.0.0.1
```

这个项目最大的收获不是「RAG 能跑」，而是给自己搭了一个能证伪的评测流程：每个设计（切块、融合、精排、HyDE）都能被一组数字支持或否定，而不是凭感觉觉得「加了应该会更好」。
