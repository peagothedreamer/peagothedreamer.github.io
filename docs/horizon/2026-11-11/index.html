「方案」 作者围绕五项改动展开：一是元数据请求，编码器把图像网格、视频时间戳、音频 token 数等布局信息以 JSON 形式交给下游，消费者据此重建占位符，无需再次抓取、解码和预处理媒体，嵌入仍经 EC 连接器传输。二是专用编码器执行路径，Model Runner V2 的 MMEncoderModelRunner 不依赖采样即可管理 GPU 完成状态，并支持 ViT CUDA Graph；在裁剪后的 Kimi-K3 检查点上，编码器只读取 96 个分片中的 2 个，权重加载从 683 秒降到 0.31 秒。三是远程传输，NIXL+CPU EC 与 Mooncake EC 两条路径落地，且按模态实测输出宽度（如 Qwen3-Omni 视觉 8192、音频 2048），避免用单一隐藏维度推断缓冲区；传输失败时，仅有元数据的消费者会明确报错而非走不安全回退。四是 Mooncake Store 跨编码器复用，在 2E+4PD、InternVL3_5-38B 的重分配实验中，512 次重复图像编码降为零，TTFT p50 从 1.209 秒降至 0.819 秒，p90 从 1.656 秒降至 0.891 秒，但这是每张图都被重分配的最佳情况。五是编排层，Python 代理减少 JSON 与响应字节的重复编解码，vLLM Router、SMG、llm-d 分别提供 HTTP、gRPC 和 Kubernetes 集成。在 DeepSeek V4.1 Flash 的 MP-DocVQA 测试中，计入全部 12 块 GPU 后，并发 64–128 时 EPD 每 GPU 吞吐比 8 卡 PD 基线高 6.6–9.5%，P90 TTFT 低 44–47%；但并发 16 时更差，32 时大致持平。作者也承认当前限制：编码器 TP=1、不支持动态 LoRA、异步发布可能让并发冷请求重复计算。

「背景」 作者一贯反对“胶水工作”——即那些不在正式流程内、只能靠工程师自愿承担才能完成的软性协调事务，如组织会议、写报告、更新文档、带新人等。他认为，依赖无偿牺牲才能维持的流程本就该消亡。如今 LLM 承担了大部分编码工作，有人期待工程师因此能腾出手做更多胶水工作，作者却认为恰恰相反：胶水工作对公司的价值比 2010 年代更低了。

「方案」 作者给出四条理由。其一，AI 降低了交付所需的协调量：AI 代理的放大效应让单个工程师就能承接过去需要小团队的项目，而大量胶水工作正是订启动会、传状态更新这类协调事务，一个人做项目根本用不上。其二，工程师不再需要被“小心伺候”：过去最重要的协调类胶水工作是安抚难缠的人，尤其是那些影响力过大、自尊心强、觉得没被充分咨询就否决项目的“隐形守门人”；ZIRP 时代结束后，许多这类守门人已被迫离开行业或改变态度。其三，初级工程师招聘减少，经验丰富的员工不需要太多手把手带教，公司也就不再需要有人默默承担入职培训。其四，只写不读的报告可以用 LLM 自动生成——这类“证明自己在干活”的报告本就没人读，用 LLM 快速产出并无损失。但作者强调，LLM 绝不可能自动化全部胶水工作，把与其他工程师的沟通交给 LLM 是极糟的主意：查项目进度、回复别人的消息都应亲自撰写，让别人去跟你的 Claude Opus 实例对话会最快地毁掉同事关系。他的建议是：无论如何不要成为“胶水工作那个人”，让坏流程失败以便被改变，但愿意在能切实推动项目成功时做少量战术性胶水工作，大部分时间仍应花在代码上——驱动 AI 代理并使其与公司价值观对齐。

「启示」 作者的核心论点是：AI 削弱了胶水工作的必要性，却无法替代其中的人际沟通，因此工程师应避免被贴上“胶水人”标签，把主要精力留给代码与 AI 代理，只在必要时做少量战术性协调。
