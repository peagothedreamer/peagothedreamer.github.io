Apache HTTP Server mod_http2 曝出严重 RCE 漏洞并已发布补丁 ⭐️ 8.0/10

Apache HTTP Server 的 mod_http2 模块被披露存在一个可远程执行代码的严重漏洞，相关补丁已发布。Wiz 的博客文章给出了该漏洞的编号 CVE-2026-119618，但未提供受影响版本范围、利用条件或攻击复杂度等细节。社区评论指出，这可能是自 2021 年以来 Apache httpd 首个被评为“critical”级别的问题，并贴出了指向 httpd 安全公告页面的链接。目前可确认的是补丁已存在，而漏洞的实际影响范围仍需以官方公告为准。

hackernews · soheilpro · 11月12日 02:11 · 社区讨论

「背景」 该漏洞编号为 CVE-2026-119618，位于 Apache HTTP Server 的 mod_http2 模块中，根源是 assign_headers() 函数在并发执行时对共享资源同步不当，导致堆内存破坏，进而可能被利用实现远程代码执行。据 NVD 记录，受影响版本为 Apache HTTP Server 2.4.55 至 2.4.70，以及 GitHub 上 mod_h2 2.0.8 至 2.0.42。Red Hat 产品安全团队将其评为 Critical，并指出公开研究已演示了针对启用 mod_http2 的默认配置服务器的可靠利用。

「运维影响」 运行受影响 Apache httpd 实例的管理员需要尽快应用补丁；若选择临时停用服务，评论者 rurcliped 提醒，certbot 的 cron 任务或 systemd timer 可能重新启动 httpd，因此仅执行“systemctl disable –now apache2”在部分 Let&#x27;s Encrypt 常见配置下不足以让服务保持关闭。

「社区讨论」 有评论者认为 HTTP/2 带来的理论收益不足以抵消其增加的复杂度，不应被如此快速推进；也有人表示自己十多年未接触 Apache，原以为市场已主要转向 nginx 等方案。这些属于个人观点与经验，并非对漏洞严重性的独立验证。

vLLM-Omni 在 Vera Rubin 上实现 H3-Image 原生 4K 服务 ⭐️ 7.0/10

rss · vLLM Blog · 11月12日 00:00

「背景」 MiniMax 的 H3-Image 是开放权重的文生图与图像编辑模型，单检查点六步采样即可输出原生高分辨率图像，无需放大模型。vLLM-Omni 团队希望验证：在 NVIDIA 新一代 Vera Rubin 上，这套扩散负载能否同时做到交互级延迟与可观的吞吐。

「方案」 作者从 vLLM-Omni 的 H3-Image 实现与 vLLM 的 Rubin 支持出发，做了两处改动：把扩散线性层接入 vLLM 的在线 MXFP8 加载与内核选择（Rubin 上合格 DiT 线性层用 FlashInfer CuTe-DSL MXFP8 GEMM，注意力用 TRTLLM_ATTN，文本编码器与 VAE 保持原生精度）；并修复重复 4K 请求在输出传输路径上的卡顿，把最终图像布局转换移到 CPU、在传输解码后的 uint8 张量之后完成。优化围绕三个目标展开：DiT 计算用 MXFP8 与 Ulysses SP4 分摊序列、DiT TP1 复制权重、AdaLN 缓存复用条件投影；解码把 VAE 的独立图像块分到多 GPU，再叠加 CUDA Graph 重放与多 CUDA 流；小显存卡则用逐层 CPU offload 换取单卡部署。在固定 4K、无参考图、六步、MXFP8 的 160 请求语料上，四卡 SP4 在并发 1 时中位延迟 0.866 秒（p95 0.944 秒），比 GB200 快 2.21 倍、比 GB300 快 1.64 倍；四个单卡副本（SP1×DP4）在并发 8 时达 6,115 张/小时，中位延迟 4.411 秒，而 SP4 在并发 2 时为 4,407 张/小时。作者特别澄清 0.87 秒来自短提示服务基准，与 1,292 字符咖啡产品提示的 1.09 秒不是同一请求。一个 BF16 对照显示，仅 VAE 解码就从 2.635 秒降到 0.213 秒，端到端约 4.0 秒降至 1.6 秒。作者也承认 1K 结果是 2048 生成后缩放、并非原生 1K 计算，跨硬件数据来自社区各自负载、不可直接比较，经济性测算基于假设售价与外推产能、未计运营成本。

「启示」 作者的核心结论是：在扩散模型服务中，解码阶段与并行策略的取舍往往和 DiT 计算同样决定端到端体验，而亚秒延迟与峰值吞吐是两个需要分别优化的工作点。
