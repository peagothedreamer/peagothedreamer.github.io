据 ABC News 报道，特朗普政府已向进口商支付累计 1000 亿美元的关税退款。报道未提供退款的法定依据、具体时间范围或涉及商品范围。

google_news · ABC News - Breaking News, Latest News and Videos · 10月20日 10:30

「背景」 美国最高法院此前裁定，总统特朗普依据《国际紧急经济权力法》（IEEPA，一项允许总统在紧急状态下管制进口的法律）征收全面关税的做法越权，联邦法官随后下令将已征收的税款退还给进口商。据 ABC News 援引一份法庭文件报道，截至 7 月底，美国政府已退还约 1000 亿美元，超过其欠数千家美国企业的 1660 亿美元总额的一半。

「对市场的影响」 退款直接流向进口商，而非最终消费者；据 OpenClassActions 报道，多数公司在第二季度财报中将其体现为利润率改善，而非下调售价。大型企业主导受益：据 Forbes 援引的数据，员工 500 人以上的公司仅占进口商总数的 2.7%，却占进口金额的近 70%，因此退款对大型进口商及其股东更为有利。

NVIDIA 定制 HBM 拟将内存控制器移入 3nm 基础裸片 ⭐️ 7.0/10

据 Silicon Atlas 援引《首尔经济日报》的报道，NVIDIA 计划将其定制 HBM（NVHBM）的底部基础裸片交由台积电 3nm 逻辑工艺制造。该设计把原本位于 GPU 内的内存控制器移入基础裸片，并搭配重新设计的 PHY，从而形成更窄的定制内存链路，为 GPU 腾出更多计算面积。NVIDIA 称 NVHBM 相比标准 HBM4E 每堆栈带宽最多提升 30%、HBM 功耗降低 15%，但这些均为厂商数据，未经独立测试；亚马逊 Annapurna Labs 是首个公开的合作方，尚无具体芯片被点名。该消息目前仅来自单一社交媒体帖文转述的二手报道，NVIDIA 与台积电均未确认。

twitter · Silicon Atlas · 10月20日 16:15

「背景」 标准 HBM 将内存控制器和 PHY 放在 GPU（XPU）裸片上，由 GPU 为每个内存堆栈管理读写与刷新时序。NVIDIA 的 NVHBM 方案则把控制器移入 HBM 堆栈底部的 base die，并搭配重新设计的 PHY，DRAM 核心层本身不变，定制的是 base die 及其与 XPU 的接口。据外部报道，这一 base die 拟采用台积电 3nm 逻辑工艺，且需要三星与台积电协同的制造方式，而非传统 HBM 的“交钥匙”模式。

「影响」 若该架构落地，内存控制器逻辑将由 NVIDIA 设计、由内存合作伙伴验证并供应，GPU 与 HBM 之间的分工和验证责任随之改变，采用方需要适配更窄的定制链路而非标准 HBM 接口。由于尚无确认和具体芯片，相关设计方与采购方目前只能将其视为待验证的方案。

「背景」 面对大语言模型（LLM）进入编程、数学等技术领域，一种常见的反对理由是：这些领域的本质是艺术，而非单纯解决问题。Sean Goedecke 认为，这种论证对工程师或许有吸引力，却很难说服普通公众和雇主，因为它忽视了公众支持技术领域的实际动机。

「方案」 作者先重构了“技术即艺术”的论证：编程和数学的价值在于创造美、表达人性或沉思无限，因此用 LLM 加速解题会错失重点。他承认自己也能欣赏数学证明和优雅代码的美感，但指出这种说法对非技术受众几乎无效。普通人的支持逻辑是：他们享受现代技术成果，知道数学和编程对维持技术进步必不可少，因此愿意尊重数学家并接受工程师的高薪；他们只把艺术性视为可能催生创造性突破的附带价值。若直接说“LLM 能加速解题，但真正的目的是艺术”，公众会像遇到坚持用手工工具装修厨房的工匠一样感到被辜负，雇主更不会买账。因此作者主张，捍卫者需要把艺术价值与实用技术价值连接起来，例如论证优雅抽象需要人类创造力、数学进步依赖新抽象、灵感需要“吊床时间”、伟大软件需要人类灵感。但他也坦承这些论点证据不足：他尚未见到 LLM 生成的代码库真正撞墙，也不认为 LLM 必然无法创造新抽象或产生类人灵感，甚至质疑伟大产品是否必须配伟大代码。

「启示」 作者的核心结论是：与其说技术工作是艺术所以有价值，不如正面论证艺术性如何让技术工作更有效；否则就等于放弃了公众认为技术工作重要的主要理由。这一论证本身也提醒我们，技术社群内部的美学辩护需要转化为面向公众和雇主的实用论证。

vLLM 推出 TorchTPU 后端：复用模型代码运行于 TPU ⭐️ 5.0/10

rss · vLLM Blog · 10月20日 00:00

「背景」 vLLM 此前主要面向 GPU 推理，而 Google Cloud TPU 用户若想使用 vLLM 的调度器、KV 缓存管理和 OpenAI 兼容服务，需要额外的适配工作。Inferact 与 Google 合作推出 vllm-torchtpu，目标是在不改动模型代码的前提下，让 vLLM 现有模型直接跑在 TPU 上，同时保持与其他硬件一致的 CLI 和服务体验。

「方案」 作者介绍，vllm-torchtpu 是一个 out-of-tree 平台插件，通过 vllm.platform_plugins 入口被自动加载；模型走 vLLM 标准 runner，经 torch.compile(backend="tpu") 下沉到 XLA，每个 TPU 设备一个 worker 进程，设备间通信走 torch.distributed，因此调度器、worker、KV 缓存管理器和 API 服务器都是未修改的上游 vLLM。TPU 相关工作主要落在以自定义算子注册、在编译图中调用的 JAX/Pallas 内核上，覆盖 ragged paged attention、稠密与稀疏 MLA、融合 MoE、FP8/INT8/MXFP4/NVFP4 量化矩阵乘等。并行方面支持 TP、DP、PP、EP、PCP、DCP 六个维度并可组合，作者称大 MoE 模型常用数据并行注意力加专家并行（如单机 v7x 上 DP=8、TP=1 开 EP）获得最佳吞吐，长上下文则用 PCP/DCP 切分预填充与 KV 缓存。KV 卸载依赖开源 C++ 库 TPU Sync 直接读取设备缓冲区，实现零拷贝卸载到主机 DRAM，并支持跨主机预填充/解码分离与传输中重分片。投机解码、前缀缓存、多 LoRA、结构化输出和多模态均沿用常规 vLLM 参数；首次启动需数分钟编译，可用 VLLM_XLA_CACHE_PATH 复用编译产物。v7x（Ironwood）为推荐硬件并在每次 PR 上跑 CI，v6e、v5e、v5p 仍属实验性。

「启示」 作者的核心主张是：通过插件化平台层与 Pallas 内核，vLLM 能在不复制模型代码、不改变用户体验的情况下扩展到 TPU。不过该文主要是功能与路线图清单，未给出性能基准或与 GPU 的对比，编译开销和实验性硬件的实际表现仍有待验证。
