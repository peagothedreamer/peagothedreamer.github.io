Claude Code“不再询问”设置致 1,122 个 GitHub 文件泄露凭据 ⭐️ 7.0/10

安全公司 Apiiro 的分析发现，公开 GitHub 上有 1,122 个文件因提交了 Claude Code 的本地设置而暴露了凭据。这些文件是用户手动创建并提交的 .claude/settings.local.json，其中记录了通过“Don&#x27;t Ask Again”批准的命令，而部分命令本身包含密钥或密码。Claude Code 团队成员 bcherny 回应称，该文件本应仅保留在本地，Claude 创建时会自动将其加入 gitignore，并承认此前未做密钥清理，正在研究防范措施。

hackernews · shmulc · 11月7日 20:45 · 社区讨论

「背景」 Claude Code 将项目级本地配置保存在 `.claude/settings.local.json` 中，该文件用于记录开发者个人的权限与命令批准设置，按设计不应提交到版本控制。Claude Code 团队成员在讨论中表示，Claude 创建该文件时会自动将其加入 gitignore，因此此次被扫描到的文件属于手动创建并提交的情况。此前已有用户报告过这一行为，本次分析则统计了公开仓库中因此泄露凭据的具体数量。

「影响与应对」 使用 Claude Code 的团队应检查仓库中是否误提交了 .claude/settings.local.json，并确认批准过的命令中不含明文凭据；一旦推送至公开仓库，相关密钥应视为已泄露并立即轮换。

「社区讨论」 有评论者指出标题有误导性：单纯点击“Don&#x27;t Ask Again”不会泄露密码，前提是用户提交了本地设置且其中批准的命令直接包含密钥。另有用户表示对 AI 代理的权限感到不安，采用隔离网络中的临时虚拟机配合 –dangerously-skip-permissions 和限制外部服务权限的 API 代理来降低风险。

GitHub 推出 Rubicon 存储架构，内部测试达每秒 7200 次推送 ⭐️ 7.0/10

GitHub 公布了代号 Rubicon 的新 Git 存储架构，目标是支撑大量 AI 智能体并发操作同一个仓库。GitHub 称内部测试中该架构支持 5000 个智能体同时协作，每秒处理 7200 次推送，读取延迟保持在较低水平。架构上，Git 对象改存于 Azure Blob Storage，引用状态由 Ref-CAS 管理，虚拟副本负责读写，后台节点负责压缩数据包。目前 Rubicon 处于有限私有预览阶段，GitHub 表示将逐步扩大推广范围，但未公布定价或正式可用时间。

telegram · zaihuapd · 11月7日 14:12

「背景」 GitHub 此前已把绝大多数仓库的副本迁移到 Azure，并在 10 月的一篇工程博客中说明，按引用建立仲裁（per-reference quorum）将用于迁移剩余仓库，同时对象存储可让读取能力独立扩展。Rubicon 在此基础上把 Git 对象（pack 及读取加速数据）放入 Azure Blob Storage，并把引用和 pack 清单交给独立的 Ref-CAS 日志服务管理。

「对使用者的影响」 依赖智能体批量提交的团队目前无法直接使用该架构，只能等待私有预览扩围；在正式开放前，现有仓库的并发推送能力与延迟表现仍取决于当前架构。

LLM 设计 AI 系统为何频频失手 ⭐️ 6.0/10

rss · Sean Goedecke · 11月8日 00:00

「背景」 作者观察到，LLM 写普通程序尚可，但面对“用 LLM 解决问题”的软件设计任务时，常会绕开 LLM 调用，转而搭建复杂却注定失败的符号系统。

「方案」 文章以一个记忆矛盾检测工具为例：这本是 LLM 擅长的任务，但 AI 代理却构建了将自然语言转为逻辑原子再用求解器比对的符号系统，而判断两句话是否表达同一命题并无解析方法。作者在 Autodeck 项目中也遇到代理用正则或关键词分类卡片，而非再调用一次 LLM。对此他提出三种解释：训练代码多为前 LLM 时代产物，但 LLM 在其他领域能选用新技术，故不充分；RLVR 环境可能缺少调用 LLM 的凭证与 API，从而抑制此类代码；他更倾向的解释是，当前 AI 代理的软件设计能力本身不足，选错工具是常态，类似在事件驱动系统中引入同步检查。作者强调，不能以人类标准评判 LLM——能实现复杂符号求解器的人类会知道它行不通，而 LLM 却可能既聪明又愚蠢地犯下此错。

「启示」 作者的核心论点是：用好 LLM 的关键在于提前预测其擅长与不擅长的边界，从而提取价值并避免在无望方向上浪费时间和 token；这种预测之所以困难，正是因为 LLM 的能力表现看似随机。
